## 学生原话摘录与导师纠正

学生："只要通过创建限流器，那么他就会自动执行__call__。作者这里还是创建了两个对象来接受，但没使用，应该是为了代码更加可读！"

纠正：类实例化执行 __init__；对实例执行 limiter(request) 才调用其 __call__。Depends 接收已创建的可调用实例，在处理请求时由 FastAPI 调用它并解析所需参数。两个参数虽未在 chat 函数体中读取，依赖仍会执行限流检查；不是仅用于可读性。构造限流器通常发生在路由定义时，不是每次请求才创建。

学生："中间还包含了对历史窗口打开的判定，对于超出规定时间的会话，会将其丢弃。"

纠正：ApiUserRateLimiter 使用 created_at__gte=cutoff 统计时间窗口内的请求记录，不是丢弃聊天会话，也没有在该查询中删除旧记录。window=60 / 86400 是最近一分钟 / 最近24小时的滑动窗口，而非必然按日历日归零。若 billing_enabled=False，此版本的限流器会直接跳过检查，因此也不能说任何配置下都必然限流。

event_generator 是异步生成器，调用它先取得生成器对象；正文在消费者开始迭代时执行，并非取得对象就已完成模型生成。当前仅需理解这一关系，不要求阅读完整生成流程。

限流、鉴权未来有实际用途时再实现。阅读理解可以用于面试讨论，但不应把未实现的功能描述成自己的项目成果。
