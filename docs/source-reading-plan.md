# 开源代码阅读计划 — 以 Khoj 为主线

更新：2026-10-13。每个学习日 30 分钟，纳入原有 4–5 小时预算。

## 主参照项目

[Khoj](https://github.com/khoj-ai/khoj) 是主阅读对象：完整的个人 AI 助手应用，包含模型聊天、文档问答、自定义 Agent、工具与自动化，产品方向接近 Agent Workspace。它的聊天路由使用 FastAPI，但整个项目还包含 Django 等组件，并非与本项目技术栈完全一致。

之前以 Pydantic AI 示例、Google SDK 和 LangGraph 为主的安排改为按需辅助。接下来围绕同一个真实应用持续跟踪，建立模块之间的联系。

[Onyx](https://github.com/onyx-dot-app/onyx) 作为企业知识问答与 Agent 的后续对照；[Dify](https://github.com/langgenius/dify) 作为平台工程化的后续对照。当前只主读 Khoj，不每天更换仓库。

选择这些项目是因为功能与求职方向契合，不代表已全面审查其质量，也不要求照搬规模或架构。阅读源码即可，暂不部署或安装整个项目。

## Day 3 的具体入口

文件：[src/khoj/routers/api_chat.py](https://github.com/khoj-ai/khoj/blob/master/src/khoj/routers/api_chat.py)。

先看文件末尾的 chat 函数，搜索 `async def chat(`。2026-10-13 核对时约在 1613–1638 行；后续以函数名定位。

只读入口和它对 event_generator、read_chat_stream 的调用，暂不展开庞大的生成流程，也不读 WebSocket 实现。

- 5 分钟：读 README，明确这个产品为谁解决什么问题。
- 15 分钟：跟踪 chat：请求体从哪里来？业务处理交给谁？流式与普通响应如何分支？
- 10 分钟：画调用链，对照自己准备写的会议整理接口，写一个可借鉴设计、一个暂不需要的设计。

没有读懂的函数先当作黑盒，记录输入输出。当前代码使用异步业务链，本项目目前使用同步 SDK；不要为模仿函数声明而直接改成 async。

## 后续阅读顺序

1. 同一项目的请求模型与输入检查：从 ChatRequestBody 的导入追踪定义；helpers.py 中 is_query_empty 可作为小入口。
2. 同一聊天链的 event_generator：每天选一小段，先读参数获取和准备步骤，再追踪模型调用。
3. 模型接入与流式返回：从实际调用追踪到供应商实现，与自己的 Gemini 客户端对照。
4. 文档检索与工具执行：自己进入 RAG / Function Calling 阶段时，继续读 Khoj 对应路径。
5. 会话持久化、权限和失败处理：对应项目工程化阶段，再对照 Onyx 或 Dify。

后续每日具体函数范围和测试文件，由导师在安排当天核对，不要求现在通读目录。首日入口已核对；之后围绕同一应用逐步深入。

## 如何判断质量与检验计划

每日记录：固定版本文件链接（GitHub 文件页面按 y）、函数名、调用链、一个设计理由、一个局限、与自己代码的差异。区分作者明确说明和自己的推测。

每周选一个设计决定与一个测试缺口复核：它解决哪个实际问题？自己的实现有没有对应失败场景？应该现在借鉴、以后采用还是不适用？导师也需要说明建议的适用条件，有依据时修改计划。

质量检查覆盖：功能与边界输入、接口合同、输入校验、可替换模型的测试、职责和依赖、失败与资源、安全与维护。真实模型效果需人工样例或评测；源码阅读和测试不能单独证明岗位达标。

阅读用于形成自己的判断，不要求当天按开源结构重构，不替代算法、Java 与后端基础训练。
